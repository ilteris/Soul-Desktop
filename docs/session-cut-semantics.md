# Session Cut Semantics: Finalize, Snapshot, or Neither?

**Status:** Draft for discussion — not yet a commitment.
**Author:** Teddy (systems_architect), 2026-05-15
**Scope:** When does a Soul session end? What boundary does the user see, and what does the registry get? Compares Soul OS against Codex, Claude Code, Gemini-CLI, ChatGPT, Cursor, Zed.

---

## 1. The problem in one paragraph

Soul OS finalizes a session with an explicit `/finalize` command. Finalize writes a Quad (intent, rationale, fixed, next-step) plus summary to `<sid>.json` and ends the session. The next session starts fresh. This is load-bearing for cross-session memory — pulse, arc, golden-pattern distillation all key off finalize records — but it puts a verb in the user's hands they can forget, ignore, or run on a session that isn't actually "done." The result is a dirty boundary: stale in-flight sessions that never got their Quad, or aggressively-finalized sessions that the user kept working in.

Every peer product I've looked at has avoided this verb. They cut sessions implicitly. The question is whether Soul OS can adopt the same UX without losing the registry richness it depends on.

---

## 2. How peers cut sessions

### 2.1 Codex (OpenAI desktop / `codex app-server`)

**Storage:** `~/.codex/sessions/<YYYY>/<MM>/<DD>/rollout-<uuid>.jsonl`. Each session is a continuous JSONL append. Every prompt, every model turn, every tool call, every reasoning chunk lands in the rollout as it happens.

**Cut:** "New chat" in the UI starts a new rollout. There is no finalize step. The rollout file *is* the record. When the user stops typing, the session is implicitly done; when they click new chat, the next rollout begins.

**Memory across sessions:** none, structurally. Codex doesn't try to build a cross-session arc. Each rollout stands alone. Resume reads a rollout back into the app-server.

**Why it works for them:** Codex is a coding assistant scoped to a single problem at a time. There's no concept of "what was I working on last week, across these five threads." The product doesn't need it.

### 2.2 Claude Code

**Storage:** `~/.claude/projects/<project-hash>/<session-uuid>.jsonl`. Continuous append per session, one file per session.

**Cut:** `/clear` ends the current session and starts a new one. `/compact` rewrites the session into a new file with an LLM-generated summary as the new head (still no formal finalize — the summary is just another turn). No finalize verb.

**Memory across sessions:** session titles are auto-generated by an LLM from the first turn or two. The sidebar shows them sorted by recency. There is no structured cross-session record beyond "here are your past chats." If you want continuity you copy-paste, or use Claude's project-level memory (CLAUDE.md), which is manual.

**Why it works for them:** the cross-session memory layer is CLAUDE.md, not the session log. Sessions are disposable; memory is a separate, manually-curated file.

### 2.3 Gemini-CLI

**Storage:** `~/.gemini/tmp/<cwd-basename>/chats/<chat>.json`. Periodic JSON snapshots of the chat state, plus an ACP-visible session/load endpoint.

**Cut:** new chat = new file. No finalize verb. Chats are named by first prompt, kept in a tmp directory that the CLI cleans up on its own schedule.

**Memory across sessions:** none beyond the chat list. Gemini explicitly treats `tmp/` as ephemeral.

### 2.4 ChatGPT, Cursor, Zed agent panel

Same shape: thread = session. New thread cuts. Old thread is browsable history. No finalize. Cross-session memory, when it exists, is a separate "Memory" feature (ChatGPT) or a manual context file (Cursor's `.cursorrules`, Zed's `assistant_panel` context).

### 2.5 The pattern

| Product | Cut trigger | Finalize step | Cross-session structure |
|---|---|---|---|
| Codex | New chat button | None | None |
| Claude Code | `/clear` or `/compact` | None | CLAUDE.md (manual) |
| Gemini-CLI | New chat | None | None |
| ChatGPT | New chat | None | Memory feature (opt-in, opaque) |
| Cursor / Zed | New thread | None | Manual context file |
| **Soul OS** | **`/finalize`** | **Quad + summary** | **Registry (pulse, arc, patterns)** |

Soul OS is the only one with an explicit finalize verb. It is also the only one with a structured cross-session record. These two facts are connected.

## 3. Why Soul OS is shaped this way

The registry is not a chat log. It's a project-keyed memory of architectural work. Pulse, arc, golden-pattern distillation, and the trajectory scoring system all read finalize records, not raw hooks.jsonl. Specifically:

- `pulse.py` reads `<sid>.json` files to build the session activity report.
- The Recent Arc section quotes finalize summaries verbatim — "Intent / Rationale / Fixed / Next Step."
- Golden Pattern distillation (PLAYBOOK §5) requires a confidence-scored Quad to even consider a session for promotion.
- The triple-anchor pipeline keys reward signals to finalize-time `epistemic_mode` and `grounding_ref`.

None of that works without a Quad. So finalize isn't a UX choice — it's the registry's contract with the kernel. The verb is the price of the structure.

The dirty-boundary problem the user is naming is real, but it's downstream of a deeper decision: **the registry treats sessions as commits, not as logs.** A commit needs a message. The message has to come from somewhere.

## 4. The two paths

### Path A: Implicit finalize-on-cut

The user never types `/finalize`. The system finalizes the outgoing session automatically when the user starts the next thing — new chat button, switching to a different session, app quit, or N minutes of inactivity.

**What the auto-Quad looks like:**
- `intent`: extracted from the first user prompt of the session (LLM summarization).
- `rationale`: inferred from the assistant's first substantive turn or the first tool call's stated purpose.
- `fixed`: derived from the set of files modified in tool calls + commit messages, if any.
- `next_step`: extracted from the last assistant turn's closing remark, or "(none — auto-finalize)" if not detectable.
- `confidence`: 0.5 (inferred), per the existing convention. Sessions auto-finalized stay below the Golden Pattern eligibility threshold (1.0).

`/finalize` becomes the **override** — the user runs it when they want a richer Quad with deductive confidence, or when they want this session eligible for pattern distillation.

**Cost:** the typical session contributes a lossier record. Pulse and arc still work — summaries are LLM-written, not user-written, so the prose quality drops but the structure holds. Golden Pattern distillation gets fed less material, since auto-Quads are below the confidence floor. Pattern-promotion velocity slows.

**Benefit:** zero verb, zero dirty boundary, parity with peer products on the surface UX. The registry stays intact. Old finalize-time hooks (decision logging, task transitions) still fire — they just trigger on the cut event instead of the verb.

**Risk:** if the auto-Quad is bad enough that the user has to constantly correct it after the fact, the verb just moved from "finalize" to "edit-quad." That's worse, not better. The auto-summarizer has to be good enough to be ignorable on most sessions.

### Path B: Continuous-session, periodic snapshots

Drop the cut. The session is the project. There is no "this session ended, that one started" — there's one rolling stream per project, snapshotted on a schedule (every N turns, every M minutes, on demand).

**What changes:**
- The registry's atomic unit shifts from session to snapshot. `<sid>` becomes `<snapshot-id>`, and `hooks.jsonl` lives at the project level, not the session level.
- Sidebar "sessions" become bookmarks into a continuous timeline rather than discrete records.
- Resume becomes "load from snapshot X to head."
- Pulse and arc read snapshots, not finalize records.

**Cost:** this is a registry rewrite, not a UX change. Every consumer that assumes `<project>/<sid>/hooks.jsonl` has to change. Tasks linked to sessions need a new linkage model. Provider transcripts no longer have a natural per-session counterpart, which complicates the cross-provider resume story (Claude/Gemini/Pi all assume a session id round-trip).

**Benefit:** the model becomes much closer to how humans actually work — work is continuous, not episodic. Snapshots are checkpoints, not commits.

**Risk:** loses the discrete session as a unit of reflection. The Quad ritual exists in part because forcing a per-session summary makes the user articulate what they did. If there's no end-of-session moment, there's no articulation moment. The reflection layer has to move somewhere else (daily pulse? per-snapshot Quad?).

## 5. Where Soul OS already leans

The existing codebase has hints in both directions:

- **Toward Path A:** the trajectory signal (`<soul_trace>` blocks) emits per-turn intent/next-step/rationale. That's the raw material for an auto-Quad — finalize-on-cut could just aggregate the last N trace blocks instead of running a fresh LLM summarization pass. SessionStart and end-of-session hooks already exist as middleware events; "cut" is a natural new event to fire there.
- **Toward Path B:** the kernel ledger is already authoritative across providers, and the Pi orchestrator already writes hooks at a per-event granularity that's finer than session. Codex sessions are already hydrated lazily on first send — there's no spawn-at-load step, so the session-as-unit assumption is already weakened in one provider.

Path A is incremental. Path B is a registry rewrite.

---

## 6. Recommendation (for discussion)

Path A, but with a refinement that came out of the design conversation: **split Quad authoring from session closure.** The current `/finalize` does both — it writes a Quad *and* it cuts the session. Those are two different operations that happen to share a moment. Pulling them apart dissolves the dirty-boundary problem more cleanly than auto-Quad alone.

Concretely:

1. **Add `/snapshot`** — user-authored Quad checkpoint, mid-session, no closure. Filed as `SOUL-SOUL_DESKTOP-068`. Writes to `sessions/<project>/<sid>/snapshots/<ts>.json`. `confidence: 1.0`, pattern-eligible. The user can snapshot N times per session as their understanding of the work evolves.
2. **Redefine `/finalize`** — "cut the session and promote the latest snapshot to canonical `<sid>.json`." If no snapshot exists, behave as today (prompt the user for a fresh Quad). The verb still exists but does less work in the common case — articulation already happened at snapshot time.
3. **Add a kernel `cut` event** — fires on new-chat, session-switch, app-quit, N-min idle. If a snapshot exists, promote latest to canonical. Otherwise, synthesize an auto-Quad from the last K `<soul_trace>` blocks plus first-prompt extraction with `confidence: 0.5`, `epistemic_mode: inductive`.
4. **Add the finalize-nudge toast** — filed as `SOUL-SOUL_DESKTOP-067`. Adapts wording: "mid-flight" sessions suggest `/snapshot`; "winding down" sessions suggest `/finalize`.

This gives three tiers of Quad provenance, all queryable by the same pulse/arc/distillation consumers:

| Quad source | Confidence | Pattern-eligible | When it happens |
|---|---|---|---|
| `/snapshot` (or `/finalize` with author) | 1.0 | Yes | User chose to articulate |
| Latest snapshot promoted by cut | 1.0 | Yes | Cut fired, snapshot already existed |
| Auto-Quad from trace blocks | 0.5 | No | Cut fired, no snapshot existed |

Pulse and arc also gain a new capability for free: intra-session trajectory. When a session has multiple snapshots, the arc can show how intent drifted ("started intending X, snapshotted with intent Y after rationale shifted, finalized as Z"). That's a more honest map of how the work actually evolved than the single-Quad-per-session view.

**Measure** after two weeks: snapshot-per-session rate, snapshot→finalize promotion rate vs. auto-Quad fallback rate, and how often a user-authored Quad gets edited post-hoc. Those numbers tell us whether the split worked or whether the snapshot verb is just another forgotten ritual.

Path B (continuous session, registry rewrite) stays on the table if the snapshot model still produces dirty boundaries — but I'd want evidence before paying for the rewrite.

## 7. Open questions

- Does auto-finalize fire on app-quit? On crash? If the app dies without a clean cut event, do we get a stale session forever, or does the next pulse heal it?
- If the user resumes an auto-finalized session, do we re-open it (un-finalize) or fork it into a new sid? Codex's answer is "rollouts are append-only, resume just continues." Claude's answer is "compaction creates a new file." Soul's answer should probably match one of those, not invent a third.
- Task linkage: today, the active task lives in the session frontmatter. If sessions auto-cut on idle, does the active task carry over to the next session, or does the user re-bind it? (My instinct: carry over until explicitly changed — task lifespan is independent of session lifespan.)
- How does this interact with SOUL-SOUL_DESKTOP-066 (Steer button)? Steer cancels an in-flight turn and flushes a queued prompt; it doesn't cut the session. The two are orthogonal — Steer changes turn boundaries, cut semantics change session boundaries — but the spec for -066 should be explicit that the queued-prompt flow doesn't trigger a cut.
